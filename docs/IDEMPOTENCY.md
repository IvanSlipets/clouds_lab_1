# Лабораторна робота №2 — завдання 7: ідемпотентність операцій запису

## 1. Призначення

Клієнт може повторити `POST` після таймауту або втрати відповіді, навіть якщо сервер уже прийняв чи виконав операцію. Без додаткового захисту такий повтор може створити другий запис або друге завдання в черзі.

Для запобігання дублюванню в проєкті реалізовано **`Idempotency-Key`**: усі повтори однієї логічної операції з тим самим ключем і тим самим JSON отримують **збережену відповідь**, а сама операція виконується лише один раз протягом часу зберігання ключа.

Механізм застосовано до маршрутів:

- `POST /api/jobs/sports` — асинхронне створення `Sport` через SQS;
- `POST /api/sports/` — синхронне створення `Sport`.

Якщо `Idempotency-Key` не вказано, декоратор не активується. Дозволений формат ключа — **8–128 символів** із набору латинських літер, цифр і символів `.` `_` `:` `-`.

## 2. Як реалізована ідемпотентність

Основна логіка знаходиться в `project/my_project/utils/idempotency.py` у декораторі `@idempotent`. Для спільного зберігання стану між кількома ECS API tasks використано **Amazon ElastiCache Redis**, розгорнутий у Terraform (`terraform/redis.tf`). З'єднання з Redis захищене TLS.

Термін зберігання запису: **86 400 секунд (24 години)**.

1. На основі користувача з JWT, HTTP-методу, шляху та `Idempotency-Key` формується ізольований ключ Redis (SHA-256).
2. JSON-запит приводиться до канонічного вигляду із сортуванням ключів, після чого для нього обчислюється SHA-256 fingerprint.
3. Перший запит резервує ключ атомарною командою Redis **`SET ... NX EX 86400`** зі станом `processing`.
4. Після успішного виконання в Redis зберігаються fingerprint, стан `completed`, HTTP-код, JSON-відповідь і `Location`.
5. Наступний запит із тим самим ключем і даними повертає збережену відповідь, **не створюючи нове завдання та повідомлення SQS**.
6. Той самий ключ з іншим тілом повертає **`409 Conflict`**. Поки перший HTTP-запит ще обробляється, повтор також одержує `409` та `Retry-After: 1`.

Заголовок `Idempotency-Replayed` дозволяє відрізнити перше виконання (`false`) від повернення збереженої відповіді (`true`).

## 3. Результати функціонального тестування в AWS

У розгорнутій AWS-інфраструктурі **успішно виконано** `loadtest/verify_bonus.ps1`, який перевіряє ідемпотентність разом з асинхронною обробкою. Для тесту використовувалися нове унікальне ім'я `Sport`, один `Idempotency-Key` та два абсолютно однакові POST-запити.

| Перевірка | Фактичний результат |
|---|---|
| Перший `POST /api/jobs/sports` | **`202 Accepted`** |
| Повторний POST із тим самим ключем і JSON | **`202 Accepted`** |
| `job_id` у двох відповідях | **Однаковий** |
| HTTP-код, JSON-відповідь і `Location` | **Однакові** |
| `Idempotency-Replayed` для першого запиту | **`false`** |
| `Idempotency-Replayed` для повторного запиту | **`true`** |
| Той самий ключ, але інше JSON-тіло | **`409 Conflict`** |
| Підсумковий статус асинхронного job | **`completed`** |
| Отримання створеного `Sport` за `sport_id` | **Успішно** |
| Кількість записів із тестовим ім'ям у `GET /api/sports/` | **1** |
| Підсумок `verify_bonus.ps1` | **Усі функціональні перевірки пройдено** |

Скрипт перевіряє кількість записів через API після завершення job та можливого закінчення TTL локального кешу списку; окремий прямий SQL-запит для підрахунку не виконується. Поле `sports.name` також має обмеження `UNIQUE` у MySQL.

Цей тест демонструє саме вимогу завдання №7: **два однакові запити — одна операція та дві однакові відповіді**. Повторне отримання `202` означає відтворення відповіді на прийняття завдання, а не повторне виконання Worker. Кінцевий результат перевіряється окремо за `GET /api/jobs/{job_id}`.

## 4. Поєднання із завданням №6 (Amazon SQS)

Ідемпотентність використовується на **двох незалежних рівнях**:

| Рівень | Яка проблема вирішується | Механізм |
|---|---|---|
| HTTP/API | Повторний POST після таймауту або втрати відповіді | Redis повертає збережені `202`, JSON та `Location`, не створюючи новий `AsyncJob` і не відправляючи друге SQS-повідомлення |
| SQS/Worker | Повторна доставка того самого SQS-повідомлення (`at-least-once`) | `SELECT ... FOR UPDATE`, перевірка статусу `AsyncJob` та транзакція MySQL не допускають повторного `INSERT` для вже завершеного job |

Такий підхід відокремлює захист від **повторного запиту клієнта** від захисту від **повторної доставки повідомлення чергою**. Він також підтримує горизонтальне масштабування API, оскільки всі екземпляри користуються одним Redis.

## 5. Обмеження

- **TTL — 24 години:** після спливу строку той самий ключ може бути сприйнятий як новий.
- Якщо Redis недоступний на етапі резервування ключа, API повертає **`503`** і не виконує операцію; якщо збереження відповіді зірвалося вже після її виконання, можливе `503` при фактично створеному job.
- Захист застосовано лише до двох вказаних POST-маршрутів, коли клієнт передає валідний `Idempotency-Key`.
- У лабораторній зовнішній ALB використовує HTTP.
